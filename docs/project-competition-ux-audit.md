# 景区导览 AI 数字人项目评审与体验优化报告

> 审视日期：2026-08-09  
> 审视范围：游客导览、景区地图、知识库管理、数字人配置、运营分析、后端服务与生产部署  
> 评审依据：《A5-景区导览服务 AI 数字人 完整赛题》及当前仓库实现

## 1. 结论摘要

项目已经明显超过“数字人套壳问答”的完成度：游客端、管理端、两景区手绘地图、官方路线、全景入口、RAG、数字人多引擎、Live2D MotionSync、运营分析、国际化和生产部署均形成了完整产品链路。当前最有竞争力的部分是地图导览与数字人讲解融合、来源数据审计、官方路线恢复、故障降级和多语言能力。

如果以评委视角判断，项目现阶段属于“功能覆盖较完整、工程证据较强，但核心赛题闭环仍需进一步量化和收敛”的状态。下一阶段不应继续堆叠入口和装饰，而应集中证明四件事：

1. 语音问答的首个可感知反馈稳定低于 5 秒。
2. 上传到知识库的常见格式确实能进入检索并提高回答准确率。
3. 数字人的声音、口型、字幕、表情和打断行为在不同引擎下都稳定一致。
4. 评委在 7 分钟内可以无解释地走通游客端与管理端的完整业务闭环。

## 2. 当前架构判断

### 2.1 前端

- Vue 3 + TypeScript + Vite，使用 Vue Router、Pinia、Element Plus。
- 游客导览包含 `/guide/experience` 与 `/guide/map` 两个同级页面。
- 地图使用 Leaflet，手绘图、Marker、路线、全景和数字人均按图层或业务组件拆分。
- 管理端覆盖知识文档、景点、FAQ、检索测试、数字人配置、运营分析、会话、反馈和服务质量。
- 当前约有 23 个页面、106 个组件；地图组件域的拆分较好，但 `experience.vue`、地图页和知识文档页仍承担了较多编排与样式职责。

### 2.2 后端

- Node.js 原生 HTTP 服务 + SQLite，服务层覆盖问答、检索、知识构建、语音、数字人、路线、运营分析和上传。
- RAG 已具备关键词/混合检索、FAQ 缓存、会话上下文、越界问题保护和回答质量标签。
- 静态地图数据由迁移脚本生成并随发布包提供，生产不依赖来源小程序接口。
- 服务端已有健康检查、数据备份、生产 release 目录和 systemd/Nginx 部署流程。

### 2.3 数据与内容

- 灵山地图迁移为 218 个点位、13 条库存路线、19 个全景记录；游客地图仅展示官方路线。
- 拈花湾迁移为 277 个点位、7 条官方路线、15 个全景记录。
- 官方路线保留道路轨迹，不用景点间直线冒充步行导航。
- 坐标、路线、图块、全景和媒体均有机器可读审计报告，异常项未被静默修正。

## 4. P0：答辩前必须解决

### 4.1 把“总响应耗时”改造成“可感知时延”

当前游客页面主要调用完整问答接口，等待回答完成后才展示并开始数字人播报；后端虽有流式能力，但前端主链路没有充分利用。因此只优化模型总耗时并不能保证体验低于 5 秒。

建议建立以下四个指标：

- `firstFeedbackMs`：用户发送后出现思考状态的时间，目标 < 150ms。
- `firstTokenMs`：收到模型首个有效文本的时间，目标 P95 < 2.5s。
- `firstSentenceMs`：首句可展示时间，目标 P95 < 3.5s。
- `firstAudioMs`：首句数字人开始发声时间，目标 P95 < 5s。

实现上应采用“检索完成 → 流式生成 → 句级切分 → TTS 队列 → 数字人播放”的流水线。后续句子继续生成时首句已经播放；用户打断时同时取消 LLM、TTS、Audio、WebRTC 和字幕队列。高频 FAQ 继续命中缓存，但页面必须标识来源和实际耗时，不能用本地固定答案伪装云模型响应。

### 4.2 让 PDF/XLSX 上传真正进入知识库

本轮增加的 PDF/XLSX 功能解决的是“安全预览与维护”，并不等于这两类文件已经进入 RAG。当前知识构建主要处理 DOCX、Markdown 和纯文本；如果评委上传 PDF 后立即提问，而后台仍显示 0 个切片，会直接削弱“知识库管理”的得分。

建议：

- PDF：优先提取文本层；扫描件进入 OCR 队列，并显示“需 OCR/处理中/已索引/失败原因”。
- XLSX：按工作表、表头和业务行转换为带来源定位的语义记录，不直接把整张表拼成无结构长文本。
- 文档更新：使用内容哈希做幂等；同名不同内容产生新版本，并保留版本关系和回滚能力。
- 删除/停用：同步移除对应切片，防止旧内容仍被检索。
- 验证：上传一份只包含新事实的文件，重建后现场提问，并在答案中展示文件名、工作表/页码和片段。

### 4.3 固化数字人的正式演示链路

正式演示必须提前锁定一个主引擎和一个降级引擎。建议讯飞作为主演示，Live2D 作为本地降级；不要在答辩中临时切换多个模型证明“数量”。

验收至少包括：欢迎语、事实问答、长讲解、暂停、继续、打断、切换景点、TTS 失败和 WebRTC 失败。需要分别记录声音、字幕、口型和表情是否同时停止。官方 MotionSync、Live2D Core、模型、讯飞形象和音色均需准备授权说明，不能把“真实音频频谱驱动”描述成已经获得逐音素精度。

### 4.4 保证全景演示不依赖失效第三方页面

迁移报告已指出部分 720 云资源存在产品过期和 iframe 风险。答辩主路径不应依赖不可控第三方页面。至少准备一个已授权、HTTPS 可访问、允许嵌入和全屏的稳定全景样例；其余入口可明确标注“第三方内容暂不可用”，并保留封面、介绍和返回地图能力。

## 5. P1：显著提升评委观感

### 5.1 收敛顶层导航与模板功能

现有桌面截图同时出现顶部菜单、工作标签、全局搜索、全屏、语言、通知、主题、用户入口和业务页面工具。对管理系统模板而言完整，但对比赛演示会分散注意力。

建议增加“比赛演示模式”，只保留：

- 游客导览
- 知识库管理
- 数字人配置
- 运营分析
- 语言与用户入口

注册页仍存在 TODO，模板中的烟花、锁屏、升级日志、通用聊天窗和部分全局工具若不参与赛题闭环，应从演示导航中隐藏；未接真实数据的通知或快捷入口也应隐藏，而不是保留空壳。目标不是删除框架能力，而是让评委第一眼只看到与评分项直接相关的入口。

### 5.2 拆分三个超大页面

当前 `experience.vue` 约 900 行、地图页面约 850 行、知识文档页面在本轮后约 760 行。它们已经不是无法维护，但状态、样式和业务编排高度集中，后续容易出现“改一个浮层影响另一个浮层”的回归。

建议拆分：

- AI 导览：`GuideChatPanel`、`GuideInputBar`、`AnswerFeedback`、`SpotNarrationPanel`、`RouteRecommendationPanel`。
- 地图页面：页面只保留景区切换和业务编排，状态恢复、讲解联动和全景入口继续下沉 composable。
- 知识文档：`KnowledgeSummaryCards`、`DocumentUploadQueue`、`DocumentTable`、`DocumentPreviewDrawer`。

拆分目标不是追求文件数量，而是让每个组件只拥有一个可描述的状态机，并能单独测试。

### 5.3 统一状态和用词

管理页面当前可能显示 `uploaded`、`processed`、`failed`、`not_built` 等英文内部状态。正式产品应全部翻译为用户可理解的状态，并在失败时展示原因和操作建议。建议统一为：待处理、处理中、已索引、仅存储、内容重复、处理失败。

“AI 路线”“官方路线”“景区道路轨迹”“实时导航”必须继续严格区分。官方路线可以称为“景区推荐游线”，但不得宣称具备实时绕行、施工封路或无障碍路径能力。

### 5.4 做好真实数据与演示数据隔离

后台已有生成演示数据的能力，但演示批次必须带明显标签；真实会话、真实评分和导入行为数据不可混在同一趋势图中。建议增加数据来源筛选和“演示数据”角标，答辩时先清理演示批次，再用现场问答产生一条真实记录展示闭环。

## 6. P2：上线后的工程优化

### 6.1 性能

- 对游客端分别统计地图、数字人、问答、TTS 和全景的资源体积与初始化时间。
- PDF.js、SheetJS、运营图表、数字人 SDK 均保持按路由/按功能加载。
- Marker 与路线已避免重建地图实例；下一步增加长任务、内存和弱网监控。
- 对 390×844 的移动端限制 PDF 画布 DPR 与 XLSX 可见行列，避免大文档导致内存峰值。

### 6.2 可访问性

- 继续补齐键盘操作、焦点回到触发按钮、抽屉焦点陷阱和屏幕阅读器标签。
- 所有小动画遵守 `prefers-reduced-motion`。
- 评分、路线节点和地图控件不能只用颜色表达状态。
- 对半透明面板做 WCAG 对比度抽测，尤其是手绘图和复杂背景上的文字。

### 6.3 安全与运维

- 文档列表、上传、文本预览和二进制内容均应只对管理员开放；上传文件使用内容哈希、类型白名单、大小限制和安全文件名。
- PDF/XLSX 在浏览器 Worker 中解析，服务端不直接执行文档内容；依赖固定版本并保留安全审计。
- 本轮升级 SheetJS 后，服务端生产依赖审计为 0 项漏洞；前端现有依赖链仍报告 1 个严重、36 个高危、35 个中危和 1 个低危项，主要来自旧版 Vite/Tailwind 构建链、Element Plus、富文本编辑器及其传递依赖。不要使用 `audit fix --force` 直接改写整套技术栈，应单独建立升级分支，先区分运行时依赖与构建期依赖，再逐组升级和回归。
- 生产环境应关闭默认演示模式，密钥只放受保护环境文件，发布前检查日志和上传目录不进入 Git。
- 保留 release、SQLite 在线一致性备份和上传文件备份，发布后验证根域名、www、HTTPS、健康检查和静态资源缓存。

## 7. 推荐删除或隐藏的冗余

| 项目 | 建议 | 原因 |
| --- | --- | --- |
| 未实现的注册入口 | 演示环境隐藏 | TODO 会让评委继续追问账号体系完整性 |
| 与赛题无关的模板烟花/装饰效果 | 不进入主包或演示导航 | 与“自然、稳重的景区导览”不一致 |
| 无真实数据的通知、聊天或快捷工具 | 演示模式隐藏 | 空入口比没有入口更影响完整度判断 |
| 重复的顶层导航 + 工作标签 | 保留一种主导航，标签仅用于后台多任务 | 减少首屏认知负担 |
| 内部英文状态码 | 改为本地化标签，详情中保留技术码 | 管理人员不应理解 `not_built` 才能操作 |
| 同一页重复解释“AI” | 改为业务动作：问答、讲解、路线、反馈 | 让产品先像景区服务，再体现 AI 能力 |

## 8. 建议的 7 分钟演示脚本

1. **0:00～0:45**：一句话说明景区痛点和双端架构，直接进入游客导览。
2. **0:45～2:10**：语音询问事实问题，展示首句时延、来源、数字人口型、字幕和打断。
3. **2:10～3:25**：打开景区地图，切换两个景区，查看手绘图、设施筛选和官方道路路线，从节点开始讲解。
4. **3:25～4:10**：进入一个稳定全景点位，退出后恢复地图和讲解状态。
5. **4:10～5:20**：后台批量上传含新事实的文档，展示去重、进度、预览、索引状态和来源定位。
6. **5:20～6:00**：回游客端询问新事实，证明知识库更新生效。
7. **6:00～6:40**：提交评分，后台查看会话、反馈和服务质量变化。
8. **6:40～7:00**：展示断网/数字人失败降级和关键量化指标。

## 9. 可量化的完成标准

答辩前建议达到以下门槛：

- 景区事实问答冻结测试集不少于 100 题，准确率 ≥ 90%，并保留引用证据。
- 语音问答 `firstAudioMs`：P50 < 3.5s，P95 < 5s；总完成时间另行统计。
- 讯飞主引擎 30 次连续问答无白屏、无双音源、无无法停止的播放。
- Live2D 降级引擎四个模型均可加载、播报、暂停、打断；失败时 2 秒内进入文字/普通音频降级。
- DOCX、MD、TXT、PDF、XLSX 各准备 1 个标准样例，上传、预览、索引和检索状态可追踪。
- 地图在 1920×1080、1366×768、768×1024、390×844 下无横向滚动和关键遮挡。
- 根域名和 www 均为 HTTPS，HTML 不缓存、哈希静态资源长期缓存，回滚演练成功。
- 所有来源手绘图、文案、音频、模型和全景有授权清单；不能确认的内容不进入主演示素材。

## 10. 最终判断

当前项目不缺功能，最需要的是“证据化、流水线化和减法”。若完成 P0 项并把演示模式收敛到核心闭环，项目可以从“功能很多的工程作品”提升为“评委能快速理解、能量化验证、具备真实景区落地可信度的产品”。后续新增功能应以是否直接提高 40 分功能完整度、30 分技术创新、20 分行业体验或 10 分文档质量为判断标准；不能贡献明确评分证据的入口，优先隐藏或延后。
